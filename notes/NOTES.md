# Upstream findings log

Running log of things found while building the Fortran shim, kept because
they're evidence for the writeup ("we understand this model well enough to
trust gradients through it") and because a couple of these are the exact
"plausible but wrong" failure mode the three shim tests exist to catch.

Upstream: `https://github.com/NOAA-OWP/snow17`, vendored as a submodule at
`external/snow17`, pinned to `ea142f94a4788ddf0be7b4d7da59c1f9f552df45`.

---

## TPREV: the upstream driver never updates it after a cold start

**What we found:** `snow17_shim.f90` sets `tprev_io = tmp(t)` after every
`EXSNOW19` call, so the next timestep sees the true previous day's air
temperature — the physically sensible reading of "previous air
temperature" (`CS(19)`/`TPREV` state contract in CLAUDE.md).

Validating against the reference output shipped in
`test_cases/ex1/output/output.snow17bmi.HHWM8I{L,U}.txt` (46 years, daily,
generated by the same `EXSNOW19`/`PACK19` via the upstream BMI driver), we
got:

- `raim` and `sneqv` (SWE): match to float32 precision, every timestep,
  over the full 46-year record.
- `snowh` (snow depth): diverges — up to ~50% relative error at times,
  though it resets to exactly 0 whenever the pack fully melts out (so it's
  bounded per-season, not runaway COMMON-block leakage).

**Root cause:** `PACK19.f` computes `DTA = TA - TPREV` and feeds it into
the density/compaction submodel (`SNOWT.f`/`SNOWPACK.f`), which is what
`snowh` depends on. Neither `PACK19.f` nor `EXSNOW19.f` ever writes back to
`TPREV` — confirmed by grep, only one read site (`PACK19.f:39`). The
caller is responsible for threading it.

In `external/snow17/src/share/runSnow17.f90`, for a cold-start run
(`warm_start_run = 0`): `modelvar%tprev(:)` is allocated and set to `0.0`
once (`modelVarType.f90:65`), passed into `exsnow19` every timestep
(`runSnow17.f90:168`), and **never reassigned anywhere else in the driver**
(grep across `runSnow17.f90`/`ioModule.f90` for other write sites turns up
only the warm-start state-file read path). So the reference output was
generated with `TPREV` pinned at `0.0` for all 16,801 timesteps of a
46-year run, not the previous day's temperature.

**Proof, not assumption:** replaying the same run with `TPREV` pinned at
`0.0` every step (`tests/test_shim.py::test_snowh_divergence_is_explained_by_upstream_tprev_bug`)
reproduces the reference `snowh` to float32 precision. That confirms the
divergence's exact cause rather than leaving it as an unexplained mismatch.

**Decision:** keep the shim's current behavior (thread the true previous
temperature). It only affects the `snowh` diagnostic — not `raim` (what
feeds HBV) or `sneqv` (the mass state) — and it's the physically correct
reading of the variable. Flagging this as a probable dead/incomplete
feature upstream (comment `c AWW ADDED 2016` on `TPREV` in `exsnow19.f`
suggests it was added for warm-start continuity and the cold-start wiring
was never finished) — same bug class already flagged in CLAUDE.md item 5
(`DATA`-initialized variables that are also assigned during execution).
Not yet reported upstream; worth a second look before filing, per the
CONTRIBUTING caveat that all upstream contributions go to the public
domain — no project code goes in that report, just the observation.

## SCF applies only to the snow fraction of precip, not rain

**What we found:** a naive mass-balance check (`sum(pcp) * scf` as total
input) was off by ~25% over a water year, even with zero net change in
storage (`sneqv` back to 0 at both ends of the period).

**Root cause:** `PACK19.f:134`, `SFALL = PXI*FRACS*SCF` — the gauge
undercatch correction factor `SCF` is applied only to the snowfall
fraction (`FRACS`), determined by a hard `TA` vs. `PXTEMP` threshold
(`PACK19.f:104`, since we run with `LAEC=0`, no rain/snow elevation curve,
no partial mixing — `FRACS`/`FRACR` are exactly 0 or 1 every timestep).
Rain (`FRACR` branch) is not rescaled. This matches the physical
motivation for `SCF` (gauges under-catch wind-blown snow, not rain).

**Where this matters:** `tests/test_shim.py::test_mass_balance` computes
the corrected input per-timestep as `pcp * scf if tmp <= pxtemp else pcp`,
not a blanket `pcp * scf`. With that correction, mass balance closes to
float32 precision over a full water year.

**Relevance to the Tesseract wrapper:** once `PXTEMP` is relaxed to a
sigmoid (per CLAUDE.md, so `d(loss)/d(PXTEMP)` isn't zero almost
everywhere), the rain/snow split becomes a smooth partial mix rather than
a hard 0/1 flag, and `SCF` will apply to a fractional `FRACS` instead.
Worth re-running this mass-balance check once that relaxation lands, to
confirm the softened split still conserves mass.

## ADC(11) vs ADC(12) dimension mismatch — confirmed harmless in our call path

See CLAUDE.md's "KNOWN BUG" section for the mismatch itself
(`exsnow19.f: REAL ADC(11)` vs `PACK19.f: DIMENSION ADC(12)`). Traced every
site that indexes `ADC` directly (`adjc19.f`, `aesc19.f`, `aeco19.f`): all
interpolate over 11 points (`N`/`N+1` capped at 11, loop bounds `2..11`),
and the only path that walks further (`UPDT19`, called from `PACK19` when
either `IUPWE` or `IUPSC` data-assimilation flags are set) is unreachable
in our usage — `EXSNOW19` hardcodes both to `0` every call. So element 12
is never actually read in the configuration we use. `snow17_shim.f90`
still pads to a 12-element array defensively (matches PACK19's declared
dummy size, costs nothing), per CLAUDE.md's workaround, but this is a
latent declaration mismatch, not a live silent-corruption bug for us.
